## 0. 摘要

知乎沉淀了中文互联网上密度最高的一批"来自真实问题的知识"。但用户的消费行为里存在一个结构性失败：**收藏即知晓的幻觉** —— 点赞收藏的一刻获得了"我学到了"的满足感，于是此后再也没有真的去读。"收藏夹吃灰"是知乎站内被反复讨论、却始终没人解决好的真问题。

现有的解法分成三类，各差一步：稍后读工具解决「**存**」，年度报告解决「**看**」，知识图谱工具要求用户「**做**」。**没有人解决"不知不觉地长出来"。**

知了森林做了一个决定性的取舍：**不要求用户做任何事**。你继续正常刷知乎，AI 把内容归纳成主题，长成树与叶；每天打开，森林因为昨天的行为自动多长一点。用户在"零操作"中获得两样东西：一片看得见的**成长感**，和一份说不清由来的**自我认知**。

名字里的「知了」是双关 —— 知了是蝉，也是「知道了」。
**你以为你知道了，但你真的知道了吗？**

### 0.1 对知乎意味着什么（一句话版）

用户得到的是「看见自己」；**知乎得到的是一类此前拿不到的兴趣信号**。

点击、停留、划走都是噪声很大的**隐式**信号；而「修剪 / 浇水」是用户主动做出的、**主题级**的二值化表态 —— 不是"这一篇我不喜欢"，而是"**这个分支**我不感兴趣"。主题粒度的偏好比单篇更稳定、更长期、更适合刻画画像。

> 推荐系统今天做的是"算法猜你在想什么"。知了森林给了用户一个**回话的通道**——用户不需要理解模型，只需要点一片叶子。

## 1. 核心创作思路与目标用户

### 1.1 问题：一个被所有人默默忍受的结构性失败

场景很具体：在知乎刷到一篇特别好的文章，顺手收藏；第二天又收藏几篇；一个月后收藏夹里躺着两百多条。你想着"以后有空再看"，但那个"以后"从来没来。更麻烦的是 —— 当朋友问你"你最近对什么感兴趣"，你居然答不上来。

这不是用户懒。**问题出在"收藏"这个动作本身**：它在行为层面提供了一个虚假的完成感，从而取消了后续真正的阅读。

这个问题在知乎站内被反复印证，随手可检索到同类讨论：

- [知乎收藏夹 34 个夹、上千条吃灰：我把整理搬出了知乎，才发现方向一直搞反了](https://zhuanlan.zhihu.com/p/2078995245765748551)
- [为什么你的知识库会变成僵尸库？——收藏夹吃灰，不是你的错](https://zhuanlan.zhihu.com/p/2071979198063948628)
- [如何将各平台收藏的有用知识串联起来进行系统化学习？](https://www.zhihu.com/question/1929498111656567100/answer/2065514774578861895)

### 1.2 关键洞察：为什么现有工具都差一步

| 类别 | 代表产品 | 解决了什么 | 没解决什么 |
|------|---------|-----------|-----------|
| 稍后读 / 收藏管理 | Raindrop.io、Readwise、Cubox、Matter | 存得下、找得到 | **不回看**；也不告诉你"你是谁" |
| 年度报告式可视化 | Spotify Wrapped、网易云年度报告 | 情绪价值极高，是社交货币 | **一年一次**，是"回望"不是"日常" |
| 个人知识图谱 | Heptabase、Obsidian、NotebookLM | 有结构、有连接 | 要求用户**主动输入与整理**，门槛高 |
| 游戏化习惯养成 | 蚂蚁森林 | 驱动力强 | **打卡负担重**，繁重感正是主要流失原因 |

另一个信号是品类本身的失败：Pocket 在 2025 年关停，说明**"纯存储"的商业模型不成立** —— 价值必须落在"理解"而非"保存"上。

> **洞察**：存东西的工具解决"存"，年度报告解决"看"，知识图谱要求你"做"。
> **没有人解决"不知不觉地长出来"。**

### 1.3 目标用户

**核心用户：知乎重度用户**

| 维度 | 描述 |
|------|------|
| 特征 | 使用知乎 1 年以上，收藏夹 ≥ 100 条 |
| 行为 | "遇到好的先收藏，以后再读"；偶尔深夜打开收藏夹感到焦虑 |
| 痛点 | ① 收藏从没回看 ② 说不清自己真正关心什么 ③ 平台也不懂他的深度兴趣 |
| 诉求 | 想"看见"自己的兴趣结构；想被理解；**不想增加任何负担** |

我们准备了三个结构截然不同的演示画像，覆盖三种典型用户，**任何一类评委用户都能对上号**：

| 画像 | 昵称 | 特征 | 产品要替他回答的问题 |
|------|------|------|---------------------|
| 深潜型探索者 | 海沟观测员 | 兴趣集中，一个领域持续加深 | "你在人工智能上走了很远" |
| 突然转向的漫游者 | 半路改道的旅人 | 人文底色，中段冒出新兴趣 | "你最近变了" |
| 广而不深的收藏家 | 什么都想知道的松鼠 | 兴趣极度发散，没有主干 | "你收藏很多，但没有一棵树长成" |

### 1.4 五条设计原则

| 原则 | 含义 | 反面案例 |
|------|------|---------|
| **零负担生长** | 森林自动长，不要求打卡 | 蚂蚁森林的每日能量收取 |
| **AI 代劳** | 提取、归类、摘要、写日记全由 AI 完成 | 要求用户手动打标签的图谱工具 |
| **视觉优先** | 一切用图形表达，不用表格和列表 | 传统知识管理的树形目录 |
| **轻交互校准** | 只保留"修剪/浇水"两个可选动作 | 复杂的设置面板 |
| **有温度** | 用"枯萎 / 浇水 / 随风而去"代替"删除 / 保留" | 冷冰冰的回收站 |

## 2. 用户如何完成核心体验

### 2.1 完整旅程（这是产品的全部）

```
首次进入
  │
  ├─ 进入演示数据（真实账号接入见 §4.2）
  │
  ├─ AI 聚类 → 森林首次生成
  │              └──── ★ 第一个高光时刻："这是我的？"
  │
每日打开
  │
  ├─ 森林因昨天的行为自动多长一点（新叶从 0 弹出来）
  ├─ 知了精灵飞过来打招呼
  │
  ├─ ① 看「光合作用报告」—— 昨天读了什么，每天一张
  ├─ ② 打开「灵魂画像」与「农夫日记」—— 你是谁，以及这周发生了什么
  │
  └─ ③ 可选：修剪不感兴趣的枝 / 给枯萎的叶浇水
                 └──── 这就是你和算法之间的一次对话
```

**情绪曲线**：第一次打开 → **惊喜**（"这是我的？"）→ 每天打开 → **安心**（"又长了一点"）→ 一段时间后 → **感动**（"原来我是这样一个人"）。

### 2.2 关键界面一：森林（森林当主角）

- **树 = 大主题**（如"人工智能"），**叶 = 小主题**（如"RAG""AI Agent"）
- 位置与大小**完全由数据决定**：内容越多，树越大越茂盛
- 治愈系手绘风，SVG 渲染，不引入 3D（性价比极低，且手绘风本身就是平面的）
- 知了精灵在森林里飞，按状态机行动：待机 / 飞行 / 修剪 / 浇水 / 清理

### 2.3 关键界面二：灵魂画像 + 农夫日记 —— 一对互证的页面（产品的落点）

这是整个产品最终想给用户的东西。它由**两个页面**承担：一个回答「你是谁」，一个回答「你最近发生了什么」。

**一 · `/profile` = 灵魂画像（锚）**

> "你是一个**深潜型探索者** —— 你不太追热点，更喜欢把一个领域挖到底。
> 依据：最近 7 天新长出的 5 片叶子里，有 4 片都长在同一棵树上。"

- 稳定的低频身份信息：灵魂类型 + 3~5 个特质，每个特质带 `score` 与**一句话依据**
- 同页给出注意力分布（各主题内容占比），是画像的量化底座 —— 依据不是空话，能看见数

**二 · `/diary` = 变化日记（流）**

> "这周你对**心理学**的关注猛地涨了起来，一下子多长出 3 片叶子。
> 但**健身**那棵树有片叶子在枯萎 —— 你想给它浇点水（继续看相关内容），还是让它随风而去？"

- 高频的每日事件流，四类事件：`newTree` 新树 / `surge` 猛增 / `decay` 枯萎 / `revive` 复苏
- 每条带日期、事件类型、树名与一句叙事；枯萎的叶子会附「该浇水了 / 可以修剪」的行动提示

**两页是一对**：画像说"你是深潜型"，日记里那些猛增与枯萎就是它的**证据**。用户在第 1 页知道自己是什么样的人，转到第 2 页就能看见依据、并且可以当场回应它（浇水 / 修剪）。

> **为什么画像要单独成页，而不是当日记的一个条目**：日记是高频流水（每天可能一条），画像是低频身份信息（几乎不变）。把「你是谁」混进每日流水，会被 `decay`/`surge` 这类事件淹没，用户翻三屏才看到自己的画像，冲击力全失。分开之后，画像有它自己的版面（印章 + 自述 + 注意力分布），日记专心做流水 —— 两页各自完整，合起来互为证据。

### 2.4 关键界面三：按天回放（演示杀手锏）

30 帧预计算、每帧 620ms，**约 19 秒**把森林从第 1 天放到第 30 天 —— **"从荒漠长成森林"的完整过程，比直接给一棵长好的树震撼得多**。回放条支持播放 / 暂停 / 拖动，并在时间轴上标出事件节点（新树 / 猛增 / 枯萎 / 复苏）。这也是让评委**亲眼验证"生长"不是静态截图**的方式。

### 2.5 两个交互动作（全部交互）

| 动作 | 语义 | 产生的信号 |
|------|------|-----------|
| **修剪** | 不感兴趣，剪掉这支 | `FeedbackSignal(action: "prune")` |
| **浇水** | 想继续看，救活这片叶 | `FeedbackSignal(action: "water")` |

只有这两个，都是可选的，**不做就是默认状态**。

## 3. 整体技术方案

### 3.1 运行时架构（与仓库代码一致）

```
┌──────────────────────────────────────────────────────────┐
│  浏览器   Next.js 16 App Router / React 19                 │
│  封面 · /forest · /report · /diary · /profile · /card      │
│  森林场景(SVG 1200×760) · 回放条 · 分享卡(canvas 900×1200)  │
└───────────┬────────────────────────────────┬─────────────┘
            │ 服务端组件直接调用（页面数据）    │ 仅 /api/feedback
┌───────────▼────────────────────────────────▼─────────────┐
│  服务端                                                    │
│   生长/回放引擎  lib/replay.ts          按天重算森林与事件    │
│   精灵决策      lib/cicada.ts          纯函数 · 零随机       │
│   精灵落点      lib/cicada-placement.ts 代价函数避让         │
│   反馈叠加      lib/feedback.ts        不可变 · 无状态       │
│   产物解析      lib/ai/serve.ts        产物优先 → 降级兜底   │
│   REST 路由     app/api/*              统一外壳             │
└───────────────────────────────────────────────────────────┘
```

> 页面（`/forest` `/report` `/diary` `/profile`）由**服务端组件直接调用**上述引擎与产物层；同时对外暴露一套 REST 路由（统一响应外壳 `{success, data, error}`），作为**对外集成契约面**。演示前端仅对 `/api/feedback` 发起 HTTP 调用。

**核心分层原则（最关键的一条设计约束）**：

> **AI 只负责"语义判断"，不负责"状态管理"。**
> 森林的树 ID、生长、布局全部由**确定性代码**控制 —— **AI 可以失败，森林不能崩。**

### 3.2 技术选型（实测版本）

| 层 | 选型 | 理由 |
|----|------|------|
| 框架 | **Next.js 16.3.5（App Router）+ React 19.2.8** | 前后端一体，48h 内最快 |
| 语言 | **TypeScript 5** | 契约即类型 |
| 样式 | **Tailwind CSS v4** | 快速落地设计稿 |
| 可视化 | **SVG + CSS 补间**（不引入动画库，回放由定时器逐帧重算） | 手绘风本就是 2D；3D 性价比极低 |
| 数据校验 | **zod 4** | AI 产物入库前强校验 |
| 状态 | React `useState` / `useReducer` | 不做全局状态库，那是过度设计 |
| AI | **大模型（OpenAI 兼容接口，本项目产物由 `deepseek-chat` 离线批量生成，强制结构化 JSON 输出）** | 聚类 / 摘要 / 叙事质量高；接口可替换，不绑定单一厂商 |
| 数据 | **JSON 文件** | 48h 不值得引入 Postgres |
| 部署 | **知乎 AiWorks**（Next.js `standalone` → CloudBase 云函数） | 官方托管 |

**明确不用**：Redux、Three.js、Postgres、GraphQL、微服务。

### 3.3 四个关键技术决策

#### ① 树 ID 跨天稳定 —— 决定"生长"叙事成败（★ 最重要）

**问题**：如果每天全量重新聚类，今天的"人工智能"树和明天的可能变成两个不同的簇 —— **森林每天洗牌，"生长"的错觉直接崩塌**。

**方案**：把"稳定"提升为**契约级硬性约束** —— `treeId` 一旦生成，跨天不得改变（接口契约 §1）。

- 聚类时**只给新内容分类**，把已有树（`treeId` / `name` / `category`）作为上下文一起传给模型，匹配得上就复用，匹配不上才允许 `isNewTree: true`
- **校验比信任更重要**：模型返回的 `treeId` 若不在已有树中且未声明为新树，视为幻觉，必须拦截
- 契约同时规定 `treeId` 命名格式 `tree_<英文短名>`、`leafId` 为 `leaf_<树slug>_<叶slug>`，使 ID 本身可读、可人工核对

真正做到了"森林每天长一点"，而不是"森林每天换一茬"。

#### ② 布局与尺寸完全确定性 —— 零随机

**问题**：力导向等随机布局每次结果不同，树木会跳动，破坏"稳定生长"的感知。

**方案**：全链路无随机数。

- 树的位置来自**确定性布局**（归一化坐标 `{x, y} ∈ [0,1]`），后端算好交给前端，前端映射到任意视口 —— **响应式零成本**
- 叶片在树冠椭圆内按**黄金角 2.399963** 螺旋撒点（`components/ForestCanvas.tsx`），位置由索引唯一确定
- 尺寸同样由数据直接推导：树宽 `(236 + min(内容数, 30) × 4.6) × scale`，其中 `scale = 0.62 + layout.y × 0.58`（用 y 当景深，近大远小）；叶大小 `5 + min(关联内容数, 12) × 0.55`

**同一份数据渲染两次，结果逐像素相同。**

#### ③ 离线生成 + 在线只读 —— 让 AI 进入生产环境

知乎 AiWorks 的构建校验器会扫描项目内**每一个** `.js/.ts` 文件，只放行 `PORT`/`HOST`/`HOSTNAME`/`NITRO_*` 等少数内置环境变量；出现任何其它 `process.env.XXX` 即阻断打包，而官方给出的"补救"是**把密钥明文写进源码** —— 这与赛事红线（凭证不得进入仓库）直接冲突。

**因此我们采用真实 AI 产品常见的形态：批量离线生成 + 服务层只读消费。**

- 模型调用脚本放在**项目外**，密钥只存在于本地 `.env.local`
- 脚本产出的**纯内容**（不含任何凭证）落库进 `mock-data/ai/`，并用 zod 校验后才允许读取
- 线上接口**只读 JSON**：零延迟、零故障、不怕评审现场网络或额度问题
- **运行时零模型调用**：`lib/` 全目录不存在任何模型 SDK 引用或密钥读取

这条约束不是妥协，反而带来了演示稳定性：**断网也能跑完整流程**。

#### ④ 失败路径是设计的一部分：AI 可以挂，页面不能白

| 失败点 | 降级行为 |
|--------|---------|
| 产物缺失 / zod 校验不过 | `lib/ai/artifacts.ts` 返回 `null`，自动切到 `lib/ai/fallback.ts` 的**确定性降级版** |
| 归类失败 | 新内容进未归类（`category: null`），森林不变，不报错 |
| 变化检测失败 | 日记返回 `[]`，不阻塞其它模块 |
| 报告生成失败 | 显示"今天没什么特别的" |
| 最坏情况 | 读预生成森林 `expected-forest/` 兜底 |

**降级版不是占位符**：它由真实数据直接推导 —— 类别权重按百分比、事件由逐日差分算出、画像按四个可观测量打分（专注深潜 = 头部类别权重、长期在场 = 树数、阅读深度 = 最大树内容量、兴趣流动 = 枯萎叶占比）。文字不如模型灵动，但**内容依然真实、可解释**。

**原则：任何 AI 失败都不应让用户看到白屏或报错。**

### 3.4 关键算法（取自实现）

**叶子状态与树的阶段**（`lib/replay.ts`）—— 由"当天 − 最后活跃日"的间隔决定：

```ts
const gap = dayNumber - lastActiveDay;
const state = gap >= 8 ? "withered" : gap >= 4 ? "fading" : "fresh";
```

```ts
const stage = n >= 15 ? "flourishing" : n >= 8 ? "mature" : n >= 4 ? "young" : "sprout";
```

**事件判定**（`lib/replay.ts`）—— 单日新增 **≥ 3 条**记为 `surge`；`fresh` 与非 `fresh` 之间的状态跃迁记为 `decay` / `revive`。

**精灵决策**（`lib/cicada.ts`）—— **纯函数、零随机**：有用户反馈时飞到对应树执行 `water` / `prune`；无反馈时自主巡视，优先找 `fading` 的叶子（按 `lastActiveAt` 升序，并列时按 `leafId` 定序）飞过去提醒；只剩 `withered` 时 `sweep`；一切安好则 `idle`。

**精灵落点**（`lib/cicada-placement.ts`）—— 代价函数求解，**硬约束不遮挡树名（权重 1e6）与树冠（7e2）**，且不压住底部回放条，保证精灵永远"演在看得见的地方"。

**不可变原则**：每次生长生成**新快照**，不原地修改；反馈叠加（`applyOverlay`）逐帧计算，叶子在该帧尚未长出则不生效 —— 便于回放与纠错。

### 3.5 接口与安全

| 措施 | 实现 |
|------|------|
| 统一响应外壳 | 所有路由返回 `{success, data, error}` |
| 输入白名单 | `userId` 仅接受 `user-a/b/c`，非法即 `400`（同时阻断路径穿越） |
| 缓存策略 | 读接口默认 `max-age=300, s-maxage=3600`；写接口 `no-store` |
| 会话 | 演示用户存于 cookie，非法值**静默回落**到默认用户，不抛错 |
| 凭证隔离 | 无密钥读取代码；凭证全程不入源码 / 日志 / 前端响应 |

### 3.6 数据与合规

| 要求 | 我们的做法 |
|------|-----------|
| 保留署名 | 展示任何内容时一并展示作者与原文链接 |
| 不冒认创作 | 不声称内容由本应用或当前用户创作 |
| 只读最小范围 | 只读取完成任务所需的数据 |
| 如实说明 | 明确声明"**内容真实（知乎公开内容，经官方 CLI 检索），时间线为演示编排**" |

我们刻意不编造标题 —— **数据可溯源，比编造可信**，这既是合规底线，也是加分项。

## 5. 与知乎社区生态的契合点

这一节是产品的立身之本：**知了森林不是"能接知乎 API 的应用"，而是"只有长在知乎上才成立的产品"。**

### 5.1 知乎独有的优势：内容自带主题锚点

开放互联网上的内容杂乱无章，聚类无从下手。而**知乎的内容形态天然是结构化的**：问题是主题，回答是观点的展开，文章是系统化沉淀，想法是碎片。

这带来一个别处拿不到的便利：**知乎的"问题"本身就是高质量的主题锚点**。在别处需要模型从零猜测"这段话属于什么领域"，在知乎可以直接借助问题标题与内容类型（`answer` / `article` / `pin` / `question`）获得语义锚，**聚类的准确率与树 ID 的稳定性都因此更高**。

官方接口返回的最小字段集 —— `Title`、`Summary`、`LikeCount`、`CommentCount`、`FavoriteCount`、`Author` —— 恰好覆盖"主题聚类 + 质量排序 + 署名合规"三件事的全部所需，**没有一丝多余，也没有一处缺口**。

### 5.2 把沉睡资产变成获得感

知乎积累了海量的收藏与点赞行为，但其中绝大部分从未被回看 —— 这是平台侧真实存在的价值流失。"收藏夹吃灰"是社区自己反复讨论的痛点。

知了森林把这份**沉没成本转化成可见的成长感**：用户第一次看到"我的收藏居然长成了一片森林"，获得的是对平台内容资产的重新占有。**这是把平台的存量数据变成用户留存动机**，而不是再做一个消耗内容的入口。

### 5.3 修剪/浇水：回流向推荐系统的高置信度兴趣信号

这是我们认为**对平台最有价值的一点**。

- **显式而非隐式**：点击、停留、划走都是噪声很大的隐式信号，而"修剪/浇水"是用户**主动二值化表态**，置信度天然更高
- **粒度恰好在"主题"这一层**：不是"这一篇我不喜欢"，而是"**这个分支**我不感兴趣"。主题粒度的偏好比单篇粒度的偏好更稳定、更长期、更适合刻画用户画像
- **双向而非单向**：今天的推荐系统是"算法猜你在想什么"，而知了森林给了用户一个**回话的通道** —— 用户不需要理解模型，只需要点一片叶子

对平台而言，这意味着：**"用户说不清自己喜欢什么"这件事，第一次有了结构化的表达出口。**

### 5.4 长尾内容的二次分发，惠及创作者

知乎内容有强烈的"时效错位"特征 —— 一篇三年前的深度回答，今天依然是最好的答案，但它已经沉到推荐流底部。

「光合作用报告」每天从用户自己的历史里重新挑出高质量内容，把**老的高赞长文重新推回用户视野**：

- 对**用户**：日日刷新，是"日常"而非"年度"的回望
- 对**创作者**：作品获得二次曝光，长尾价值被重新兑现
- 对**平台**：内容库被反复利用，而非一次性消费

### 5.5 与社区调性一致：克制、专业、不打扰

知乎社区的文化底色是认真、专业、友善。知了森林在交互上刻意做了**减法**：

- 不打卡、不做繁重感（对照：蚂蚁森林的流失研究显示"繁重感"是主要流失原因）
- 只保留两个可选动作，**不操作就是默认状态**
- 用"枯萎 / 浇水 / 随风而去"的语气替代"删除 / 保留"，**用温度替代控制**

它不试图让用户"多用一会儿"，而是让用户"更了解自己一点"。

### 5.6 天然的自传播素材

「灵魂画像」与「分享卡片」是社区型产品最有效的自传播单位 —— 用户会主动分享"我的森林长这样"。而知乎本身就是中文互联网上**最适合讨论"我是谁、我在关心什么"的地方**，分享落回社区讨论是自然发生的，无需运营撬动。

### 5.7 可延展的第二条曲线：创作者版森林

官方能力还开放了授权用户的**创作列表与互动数据**（`LikeCount` / `CommentCount` / `FavoriteCount`）。同一套引擎可以平移成"创作者版"：

> 一个创作者的森林 = 他的创作主题分布 × 读者反馈强度。

让创作者看见"我这些年在写什么、哪些主题真正被读者接住了"。这是从**消费者侧**走向**生产者侧**的延展，也是这条赛道"知识生产"的直接呼应。

## 7. 为什么这是 AI 场景，而不是算法规则

赛道权重中「AI 场景价值」占 40%，因此有必要说清：**AI 在生成阶段是四个环节里唯一可行的解法。**

| 环节 | 为什么规则做不到 | AI 做什么 |
|------|-----------------|----------|
| **主题聚类与命名** | 内容主题无法用关键词穷举（"RAG"和"检索增强""向量召回"是同一主题），且要判断新内容该归入既有树还是长出新树 | 语义层面的归属决策，且强制输出结构化 `assignments` |
| **变化检测与叙事** | 统计差分只能算出"从 3 条变成 9 条"，说不出"你最近被心理学击中了" | 把数字差分转成第二人称的拟人化叙事 |
| **灵魂画像** | 画像不是统计报表，"深潜型探索者"是从全局结构里读出的**判断**，且必须附带可追溯的依据 | 跨全量数据的自我认知总结，输出 `soulType` + 带 `evidence` 的特质 |
| **精灵台词** | 模板可以兜底，但灵动感来自模型 | 按动作与上下文生成治愈系单句 |

**同时，我们用工程手段把 AI 的风险关在笼子里**（见 §3.1 / §3.3）：

- AI 只输出语义判断，**状态与布局由确定性代码掌控**
- 产物**离线生成、入库前 zod 校验、线上只读**
- 产物缺失即切**确定性降级版**，最坏情况有预生成森林兜底

**这让我们既能拿到大模型的语义能力，又不必在评审现场赌网络和额度。**

|----|-----------|
| **可访问性** | 森林页叶子目前仅响应鼠标事件，外层容器的 `role="img"` 会隐藏子树，**键盘与读屏用户无法进入叶子**。这是我们在 48h 窗口内主动选择不改的问题（不影响演示主流程）；修复方案已明确（叶子层改为可聚焦语义 + 键盘交互），列为下一阶段第一优先级 |
| **数据生成脚本未随仓库** | 数据集构建脚本与 AI 产物生成脚本运行在仓库之外（因其需要凭证与本地文件系统，与 AiWorks 只读约束冲突）。仓库内提供的是**产物与格式契约**，可直接复现渲染与降级路径，但**不能从零重建数据集** |
| **产物覆盖度不均** | AI 产物集中覆盖默认演示用户（28 天报告 + 日记 + 画像）；另外两个用户以画像与报告为主，其余日期走确定性降级版。页面文案对"由大模型写成"的表述**偏宽**，我们已知悉并计划在文案上如实区分 |
| **测试覆盖** | 34 项测试覆盖的是纯函数（反馈叠加、精灵决策、精灵落点、知乎检索 URL 构造）；`replay.ts`、降级层与 API 路由**尚无自动化测试** |
| **反馈不持久** | 受 AiWorks 云函数只读文件系统限制，反馈为**无状态叠加**，不落盘；真实接入时需引入服务端存储 |
| **线上 Demo 受网关配额限制** | 部署在知乎 AiWorks，网关按套餐设有 QPS 配额。首屏素材已全部改走**带退避重试的加载器**（取不到就不画，绝不显示断图），但配额紧张时素材仍可能**渐进出现**而非一次到位。这是平台侧约束，官方文档给出的解法是购买资源包提额 |

### 9.2 明确不做（不是遗漏，是主动砍掉）

| 砍掉的功能 | 理由 |
|-----------|------|
| 社交功能（拜访他人森林 / 圈子） | 48h 做不完；本赛道是"学习与知识生产"，不是社交 |
| 推送通知 | 演示环节体现不出，且需移动端 |
| 3D 化 | 性价比极低，2D 手绘风更贴治愈感 |
| 树列表展示/隐藏控件 | 森林页的定位是"森林当主角"，加控件是往回走；更好的做法是点树名收起 |

### 9.3 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 知乎数据接口不可用 | 数据管道断裂 | 已有 191 条真实数据集 + 预生成森林兜底 |
| AI 调用延迟 / 失败 | 演示卡住 | 产物离线预生成，运行时纯读文件 |
| 树 ID 不稳定 | 森林每天洗牌 | 契约强制增量归类 + 校验拦截幻觉 ID |
| 森林布局难看 | 演示效果差 | 全链路确定性布局，零随机 |
| 现场网络不可控 | 演示翻车 | 全部 AI 结果本地预生成，**断网可跑完整流程** |
